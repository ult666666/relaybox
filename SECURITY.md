# Security

RelayBox is an educational, local-only demo. It has no supported production deployment configuration or independent security audit. Do not expose it through a tunnel, reverse proxy, public interface, or shared environment containing real data.

The HTTP service uses a shared HMAC secret for ingestion and checks timestamp freshness. It refuses non-loopback binding, rejects unacceptable Host and cross-site headers, bounds JSON bodies and concurrent handlers, and uses parameterized SQL. These controls do not authenticate readers on the local machine. Any process that can access the loopback port can read stored payloads; any user with the database can change state through the library or CLI.

The public `--demo-secret` key is for synthetic data only. For local experiments, use a private random key in `RELAYBOX_SECRET`, a private database directory, and avoid putting secrets in payloads, command history, screenshots, issues, or source control. Data is stored unencrypted with no automatic retention or backup. The repository ignores `.env` and SQLite files, but this is not a data-loss prevention system.

Leases provide at-least-once processing. A stale token cannot acknowledge or fail a reclaimed job, but tokens do not prevent external side effects. Local clock changes affect leases and timestamp freshness.

Manual `backup`, `verify-backup` and new-path `restore` support only operator-owned RelayBox schema-1 and schema-2 files in trusted local directories. Backup receipts omit tokens/payloads, but the SQLite snapshot itself contains all data and private lease capabilities, unencrypted. Protect copies and retained receipts like the original. Never copy only the main file of a live WAL inbox. No arbitrary SQL, extensions, migrations or repair are run; read-only schema/integrity checks still use SQLite's file parser and are not a sandbox for hostile databases. Use current trusted Python/SQLite builds.

Snapshot operations reject existing destinations/sidecars and selected symlinks, canonicalize ancestor aliases, request `0600` files and use exclusive hard-link publication. Directories/files must not be concurrently replaced or edited by an untrusted actor; these path checks do not secure attacker-writable directories. Hard-link support is required, Windows ACLs/network filesystems are unverified, and a cooperative deadline cannot interrupt blocked OS I/O. The 1 GiB input bound is not a general storage quota. Hard kills may leave private temporary files, final directory metadata is not fsynced, and no power-loss durability guarantee is made.

Stop the original service and every original worker before switching to a restored path. Restoring preserves lease fields but creates independent fencing, so original workers can still act on their own database. Recovery can repeat work after the snapshot. Back up/retain receipt files separately; they are not in the database snapshot. Identical retained receipts support the sample handler's idempotency, without cross-database exactly-once guarantees or restoration of external effects.

If you find a vulnerability, use the repository's private vulnerability reporting option if available. If unavailable, open a minimal public issue requesting a private contact route without exploit payloads, secrets, or sensitive data. No response-time guarantee is offered. Include version, a synthetic reproduction, expected behavior, and the affected boundary after a private route is established.

## Outbound delivery

Outbound delivery sends requests, so it has its own boundary:

- **Targets.** By default a subscription URL must name a literal loopback IP address (`127.0.0.0/8` or `::1`). Host names, including `localhost`, are refused, so no DNS answer can redirect a delivery. The URL is checked when the subscription is created and again before every attempt. `--allow-remote` (needed on both `subscription add` and `deliver`) accepts other hosts, but only over HTTPS with certificate and hostname verification. It adds no filtering of private or link-local ranges (such as cloud metadata addresses), no DNS pinning and no egress proxy. The [Standard Webhooks guidance on server-side request forgery](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md) recommends an isolated network and a filtering proxy for any real deployment; RelayBox provides neither. Subscriptions are created only through the trusted local CLI and library.
- **Requests.** Redirects are never followed and proxy environment variables are ignored. Each attempt has a wall-clock deadline and reads at most 4 KiB of the response body by default (64 KiB maximum). For a remote host name, the deadline does not cover the DNS lookup, and each resolved address gets its own connection timeout, so one attempt can last several times the deadline.
- **Secrets.** Signing secrets are stored unencrypted in the database and in its backups. They are printed once when created or rotated, and listings show only a SHA-256 fingerprint. Keep that output out of shell history, issues and screenshots. Rotate with `subscription rotate-secret`; `--grace-seconds 0` retires older secrets at once after a leak. The public `--demo-secret` keys are for synthetic data only.
- **Duplicates.** Delivery is at least once. A crash or a lost lease can send the same message again with the same `webhook-id`, so receivers must deduplicate on it and verify the signature and timestamp of every request.
- **Dashboard replay.** The dashboard is read-only unless `serve` runs with `--allow-replay`. That enables one route, which requeues an outbound dead letter. It requires a same-origin `Origin`, JSON content type and empty body, which blocks cross-site pages, but any local process that can reach the port can still call it.
